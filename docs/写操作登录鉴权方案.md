# 写操作登录鉴权方案（QQ 私聊验证码）

> 状态：**方案稿，尚未实施**
> 目标：所有写数据库的操作都需要登录态；尽量不增加公网链路延迟。

---

## 一、背景与现状核查

### 1.1 链路延迟实测（2026-10-23）

| 环节 | 实测值 |
|---|---|
| 本地后端响应（本机直连 8000） | 20 ~ 57 ms |
| 公网单次请求（经穿透到美国） | **860 ~ 970 ms** |
| 后端处理占比 | **不到 6%** |

结论：**延迟由请求数决定，不由单个请求的工作量决定。**
因此鉴权设计的第一原则是：**不要在每次写操作时增加网络往返。**

### 1.2 `bqbq_client_id` 现状

它在浏览器 `localStorage` 里生成（格式 `client_xxxxxxxxxxx`，见
`frontend/src/stores/useGlobalStore.ts:75-77`），唯一用途是作为
`client_id` 字段随请求回传。

**记录覆盖率（实测）**

| 接口 | 是否记录 client_id |
|---|---|
| 规则树 20 个写接口 | ✅ |
| `PUT /images/{id}/tags` | ✅ 调用记录 |
| `POST /images/upload` | ❌ |
| `DELETE /images/{id}` | ❌ |
| `POST /system/import`、`/import/all` | ❌ |
| `GET /system/export`、`/export/all` | ❌ |

**`search_version_log` 实际数据**：仅 **64 条**，时间集中在
**2026-01-31 ~ 2026-02-04**（四天），4 个不同 client_id，此后完全空白。

**结论：`bqbq_client_id` 现在是匿名、可被用户任意清空的本机标识，
不能直接当身份体系。** 可以复用它作为"登录态载体"，但必须由后端
另行记录其权限状态，不能信任前端声明。

### 1.3 AstrBot 插件现状（关键约束）

`astrbot_plugin_bqbq_collect`：

| 事实 | 影响 |
|---|---|
| 纯**被动**接收（只有 `@filter.event_message_type` / `@filter.command`） | **无法主动发消息** |
| 没有任何 `send_message` / `context.send` 调用 | 同上 |
| 与后端同机，`backend_url = http://127.0.0.1:8000` | 通信延迟可忽略 ✅ |
| 已有 `@filter.command` 体系（如 `bqbq绑定`） | **加命令很容易** |

## 二、方案选型

### 2.1 为什么"每次写操作都问 bot"不可行

```
写标签 → 后端问 bot → bot 问 QQ → 用户确认 → 原路返回
        每次 ≈ 860ms × 多个往返
```
一次打标签可能要多等 2~3 秒。**排除。**

### 2.2 推荐方案：一次性验证码 + 后端本地签发 token

```
① 网页点「登录」→ POST /auth/request
        后端生成 4 位验证码，暂存 {code → client_id, 5 分钟过期}
        网页显示验证码

② 用户在自己的 QQ 私聊 bot，发送：bqbq登录 1234
        插件收到命令 → POST /auth/confirm {code, sender_openid}
        后端校验 code 有效 + openid 在管理员名单内
        → 把该 client_id 标记为已授权，并返回 token

③ 之后所有写请求带 Authorization: Bearer <token>
        后端**本地 HMAC 验签**（约几十微秒，零网络）
```

**延迟影响**

| 操作 | 额外延迟 |
|---|---|
| 打标签 / 改规则 / 删除 | **≈ 0 ms** ✅ |
| 登录（一次性） | 1 次 QQ 消息 + 本机 HTTP（< 1s） |
| Token 过期后重登 | 同上（有效期建议 30 天） |

### 2.3 Bot 侧改动量评估

**只需新增一个命令**，约 20 行，复用现有模式：

```python
@filter.command("bqbq登录", alias={"bqbq 登录", "bqbq认证"})
async def cmd_login(self, event: AstrMessageEvent):
    # 参数：event.message_str
    # 1. 取 4 位验证码
    # 2. 取 openid = event.get_sender_id()
    # 3. httpx POST 到 {backend}/auth/confirm
    # 4. 把后端返回的结果用 plain_result 回复
```

无需新增主动发消息能力 ✅

**管理员判定可直接复用现有设施**：插件里已有
`_is_admin(event)`（`main.py:1371`），它读 AstrBot 在事件上设好的
`role` 字段（由 AstrBot 的 `admins_id` 配置决定）。

**因此不需要自建 `auth_admins` 表** —— 管理员身份在 bot 侧判定，
bot 只把"已通过管理员校验"的确认转发给后端即可。这比让后端
维护 openid 名单更简单，也和现有代码一致。

## 三、详细设计

### 3.1 数据库表

```sql
-- 登录会话（token 只存哈希，不存明文）
CREATE TABLE IF NOT EXISTS auth_sessions (
    client_id   TEXT PRIMARY KEY,      -- 浏览器 localStorage 里的 client_xxx
    token_hash  TEXT NOT NULL,         -- sha256(token)，防止库泄露直接被用
    openid      TEXT,                  -- 授权时的 QQ openid
    created_at  TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    expires_at  TIMESTAMP NOT NULL,
    last_seen   TIMESTAMP              -- 可选：最后活跃时间
);

-- 待确认的验证码（内存缓存即可，但落库便于重启后仍可用）
CREATE TABLE IF NOT EXISTS auth_pending_codes (
    code        TEXT PRIMARY KEY,      -- 4 位数字
    client_id   TEXT NOT NULL,
    created_at  TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    expires_at  TIMESTAMP NOT NULL,
    used        INTEGER DEFAULT 0
);
```

> **不需要 `auth_admins` 表**：管理员判定在 bot 侧用现成的 `_is_admin()`
> 完成（见 2.3）。后端只信任"带正确 `X-Bot-Secret` 且声称已校验管理员"
> 的 `/auth/confirm` 请求。

### 3.2 后端接口

| 方法 | 路径 | 用途 | 是否需登录 |
|---|---|---|---|
| POST | `/auth/request` | 网页申请验证码 | 否 |
| POST | `/auth/confirm` | **bot 调用**，用户私聊确认 | 否（用共享密钥鉴权） |
| GET  | `/auth/me` | 查询当前登录态 | 否 |
| POST | `/auth/logout` | 退出登录 | 是 |

**`/auth/request`**

```jsonc
// 请求
{ "client_id": "client_abc123" }
// 响应
{ "success": true, "code": "4821", "expires_in": 300 }
```

**`/auth/confirm`**（bot 调用）

```jsonc
// 请求（需带 X-Bot-Secret 头，防止外部伪造）
{ "code": "4821", "openid": "ABC123..." }
// 响应
{ "success": true, "message": "登录成功，请回到网页继续" }
// 失败
{ "success": false, "error": "验证码无效或已过期" }
```

用户**不会**直接拿到 token —— token 由后端写入 `auth_sessions`
（按 client_id），网页下次调用 `/auth/me` 时凭 client_id 换领 token
并存入 localStorage。这样避免把 token 通过 QQ 消息明文传递。

### 3.3 鉴权中间件

新增 `backend/app/auth.py`：

```python
def require_edit(client_id: str, token: str | None) -> None:
    """写操作依赖项：校验登录态，失败抛 401。"""
    # 1. token 为 None -> 401（前端据此弹出登录框）
    # 2. sha256(token) 查 auth_sessions，匹配 client_id 且未过期 -> 通过
    # 3. 否则 401
```

在写接口上加依赖：

```python
@router.put("/{image_id}/tags")
async def update_image_tags(image_id: int, data: ImageUpdate,
                            auth: AuthContext = Depends(require_edit)):
    ...
```

### 3.4 需要加鉴权的接口清单

| 文件 | 接口 | 备注 |
|---|---|---|
| `routers/images.py` | `POST /images/upload` | bot 主通道 ！**必须保留例外**（见 3.5） |
| `routers/images.py` | `PUT /images/{id}/tags` | |
| `routers/images.py` | `DELETE /images/{id}` | |
| `routers/images.py` | `POST /images`（新建记录） | `images.py:179` |
| `routers/rules.py` | 全部 20 个写接口 | |
| `routers/system.py` | `POST /system/update_tags` | |
| `routers/system.py` | `POST /system/import`、`/import/all` | **高危** |
| `routers/system.py` | `GET /system/export`、`/export/all` | 导出建议也保护 |
| `main.py` | `POST /api/upload` | 网页上传入口 |

**只读接口（搜索、列表、缩略图、规则读取、`check-md5`）不加鉴权** ——
否则每次翻页都要验证，在网络差时会很难受。

### 3.5 关键例外：机器人上传

**机器人实际只调用两个接口**（实测 AstrBot 插件 main.py）：

| 接口 | 用途 | 是否写库 |
|---|---|---|
| `GET /api/images/check-md5/{md5}` | 预查重 | ❌ 只读 |
| `POST /api/images/upload` | 上传原图 | ✅ 写 |

所以**只需给 `POST /images/upload` 开一路例外**，范围很窄。
该接口是 bot 的入库主通道（日均上千张），若也要求登录态会全部失败。

**处理方式**：给 bot 一路专用身份 ——

```
请求头 X-Bot-Secret: <与 /auth/confirm 相同的共享密钥>
```

中间件看到该头且密钥匹配，直接放行，不要求 token。

> **注意**：该接口同时被网页上传使用（`POST /api/upload` 是另一个入口，
> 见 `main.py:579`）。两个入口要分别处理：
> · `/api/images/upload` —— bot 用，认 `X-Bot-Secret`
> · `/api/upload` —— 网页用，认 token

### 3.6 前端改动

| 位置 | 改动 |
|---|---|
| `useApi.ts` | 请求自动带上 `Authorization: Bearer <token>` |
| `useGlobalStore.ts` | 新增 `authToken` / `authExpiresAt`，存 localStorage |
| `FloatingButtons.vue` | 把一个按钮改成「登录」，显示登录态（未登录/已登录/即将过期） |
| 新增 `LoginDialog.vue` | 申请验证码 → 展示 → 提示「私聊 bot 发送 bqbq登录 XXXX」 → 轮询 `/auth/me` |
| 全局 401 拦截 | 任何写请求返回 401 → 弹出登录框，**不要静默失败** |

**轮询代价**：登录流程中轮询 `/auth/me`，间隔建议 **2 秒**，
最多轮询 **5 分钟**（与验证码有效期一致）。这是唯一新增的轮询，
且只在登录过程中发生，不影响日常使用。

## 四、延迟影响汇总

| 场景 | 现在 | 加鉴权后 | 变化 |
|---|---|---|---|
| 浏览/搜索/翻页 | 860ms × N | 860ms × N | **无变化** |
| 打标签 | 860ms | 860ms + 验签(~0) | **无感知** ✅ |
| 改规则 | 860ms | 860ms + 验签(~0) | **无感知** ✅ |
| 首次登录 | — | 一次 860ms（申请码） + QQ 消息 | 一次性 |
| Token 过期 | — | 同上 | 30 天才一次 |

**结论：不会让延迟翻倍。** 唯一新增的固定开销是登录那一次，
且可以做成长效（30 天）。

## 五、安全考虑

| 风险 | 对策 |
|---|---|
| 验证码被猜中 | 4 位 = 1 万种；有效期 5 分钟 + 每个 client_id 限次（如 5 次/小时）+ 用后即焚 |
| 验证码在 QQ 里被看到 | 私聊只有自己可见；且码只用于把 token 写进**发起请求的那个 client_id**，别人拿到码也没用（除非同时也控制了那个浏览器） |
| token 泄露 | 存 sha256 哈希；支持 `/auth/logout` 立即失效 |
| 库泄露 | 哈希后无法直接使用 |
| bot 接口被伪造 | `/auth/confirm` 需 `X-Bot-Secret`，只在 bot 与本机间共享 |
| 非管理员冒充 | bot 侧用现成的 `_is_admin()` 把关（读 AstrBot 的 `role`），非管理员直接拒绝 |

**注意**：官方机器人拿到的是 **openid 而非 QQ 号**，所以任何 openid
比较都必须用 openid 形式（可用现有 `bqbq绑定` 命令让用户自查）。

## 六、实施步骤（建议顺序）

| 步骤 | 内容 | 风险 |
|---|---|---|
| 1 | 建表 + `/auth/*` 接口 + `require_edit` 中间件 | 低（不影响现有功能） |
| 2 | 前端：token 管理 + 401 拦截 + 登录弹窗 | 中 |
| 3 | bot：新增 `bqbq登录` 命令 | 低 |
| 4 | 给写接口逐个加 `Depends(require_edit)` | **中（漏一个就是安全洞；多一个是功能中断）** |
| 5 | 机器人上传通道加 `X-Bot-Secret` 例外 | **高（漏了机器人会全挂）** |

**建议**：第 4、5 步一起做，并先用一个开关（如
`BQBQ_AUTH_ENFORCE=0/1`）默认关闭，确认无误后再打开。

## 七、待确认事项

1. **管理员是谁**：AstrBot 的 `admins_id` 里已配好（bot 侧 `_is_admin()`
   依据它判断）。确认一下这份配置是你要用的名单即可。
2. **Token 有效期**：建议 30 天，是否接受？
3. **导出是否也需登录**？导出会带出全库数据，建议保护。
4. **bot 共享密钥**如何存放？建议独立文件 `bot_secret.txt`（加入
   `.gitignore`）或环境变量，bot 与后端各读一份。
5. 是否需要**操作审计**（记录谁在什么时候改了什么）？现有
   `search_version_log` 已覆盖规则树部分（但只记录 client_id，
   不记录身份），可扩展到打标签/删除。

## 八、备选简化方案（如果连 bot 改造都想省）

**纯验证码 + 网页直接确认**（不经 QQ）：

- 验证码在网页生成并显示，用户手工输入确认。
- **缺点**：没有第二因子，等于只加了"手势摩擦"，安全性提升有限。
- **优点**：零 bot 改动、零额外网络。

如果目的是"防止误操作"而非"防外部入侵"，这个方案够用；
如果是后者，必须走 QQ 确认。
