# 写操作登录鉴权方案（QQ 私聊验证码）

> 状态：**方案稿，尚未实施**
> 目标：所有写数据库的操作都需要登录态；尽量不增加公网链路延迟。

---

## 一、背景与现状核查

### 1.1 链路延迟实测（2026-10-23）

| 环节 | 实测值 |
|---|---|
| 本地后端响应（本机直连 8000） | 20 ~ 57 ms |
| 公网单次请求（经穿透到美国） | **860 ~ 970 ms** |
| 后端处理占比 | **不到 6%** |

结论：**延迟由请求数决定，不由单个请求的工作量决定。**
因此鉴权设计的第一原则是：**不要在每次写操作时增加网络往返。**

### 1.2 `bqbq_client_id` 现状

它在浏览器 `localStorage` 里生成（格式 `client_xxxxxxxxxxx`，见
`frontend/src/stores/useGlobalStore.ts:75-77`），唯一用途是作为
`client_id` 字段随请求回传。

**记录覆盖率（实测）**

| 接口 | 是否记录 client_id |
|---|---|
| 规则树 20 个写接口 | ✅ |
| `PUT /images/{id}/tags` | ✅ 调用记录 |
| `POST /images/upload` | ❌ |
| `DELETE /images/{id}` | ❌ |
| `POST /images/upload` | ❌ |
| `DELETE /images/{id}` | ❌ |
| `POST /system/import`、`/import/all` | ❌（**接口已废弃，见 3.4.1**） |
| `GET /system/export`、`/export/all` | ❌（同上，已废弃） |

**`search_version_log` 实际数据**：仅 **64 条**，时间集中在
**2026-01-31 ~ 2026-02-04**（四天），4 个不同 client_id，此后完全空白。

**结论：`bqbq_client_id` 现在是匿名、可被用户任意清空的本机标识，
不能直接当身份体系。** 可以复用它作为"登录态载体"，但必须由后端
另行记录其权限状态，不能信任前端声明。

### 1.3 AstrBot 插件现状（关键约束）

`astrbot_plugin_bqbq_collect`：

| 事实 | 影响 |
|---|---|
| 纯**被动**接收（只有 `@filter.event_message_type` / `@filter.command`） | **无法主动发消息** |
| 没有任何 `send_message` / `context.send` 调用 | 同上 |
| 与后端同机，`backend_url = http://127.0.0.1:8000` | 通信延迟可忽略 ✅ |
| 已有 `@filter.command` 体系（如 `bqbq绑定`） | **加命令很容易** |

## 二、方案选型

### 2.1 为什么"每次写操作都问 bot"不可行

```
写标签 → 后端问 bot → bot 问 QQ → 用户确认 → 原路返回
        每次 ≈ 860ms × 多个往返
```
一次打标签可能要多等 2~3 秒。**排除。**

### 2.2 推荐方案：一次性验证码 + 后端本地签发 token

```
① 网页点「登录」→ POST /auth/request
        后端生成 4 位验证码，暂存 {code → client_id, 5 分钟过期}
        网页显示验证码

② 用户在自己的 QQ 私聊 bot，发送：bqbq登录 1234
        插件收到命令 → POST /auth/confirm {code, sender_openid}
        后端校验 code 有效 + openid 在管理员名单内
        → 把该 client_id 标记为已授权，并返回 token

③ 之后所有写请求带 Authorization: Bearer <token>
        后端**本地 HMAC 验签**（约几十微秒，零网络）
```

**延迟影响**

| 操作 | 额外延迟 |
|---|---|
| 打标签 / 改规则 / 删除 | **≈ 0 ms** ✅ |
| 登录（一次性） | 1 次 QQ 消息 + 本机 HTTP（< 1s） |
| Token 过期后重登 | 同上（有效期建议 30 天） |

### 2.3 Bot 侧改动量评估

**只需新增一个命令**，约 20 行，复用现有模式：

```python
@filter.command("bqbq登录", alias={"bqbq 登录", "bqbq认证"})
async def cmd_login(self, event: AstrMessageEvent):
    # 参数：event.message_str
    # 1. 取 4 位验证码
    # 2. 取 openid = event.get_sender_id()
    # 3. httpx POST 到 {backend}/auth/confirm
    # 4. 把后端返回的结果用 plain_result 回复
```

无需新增主动发消息能力 ✅

**管理员判定可直接复用现有设施**：插件里已有
`_is_admin(event)`（`main.py:1371`），它读 AstrBot 在事件上设好的
`role` 字段（由 AstrBot 的 `admins_id` 配置决定）。

**因此不需要自建 `auth_admins` 表** —— 管理员身份在 bot 侧判定，
bot 只把"已通过管理员校验"的确认转发给后端即可。这比让后端
维护 openid 名单更简单，也和现有代码一致。

## 三、详细设计

### 3.1 数据库表

```sql
-- 登录会话（token 只存哈希，不存明文）
CREATE TABLE IF NOT EXISTS auth_sessions (
    client_id   TEXT PRIMARY KEY,      -- 浏览器 localStorage 里的 client_xxx
    token_hash  TEXT NOT NULL,         -- sha256(token)，防止库泄露直接被用
    openid      TEXT,                  -- 授权时的 QQ openid
    created_at  TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    expires_at  TIMESTAMP NOT NULL,
    last_seen   TIMESTAMP              -- 可选：最后活跃时间
);

-- 待确认的验证码（内存缓存即可，但落库便于重启后仍可用）
CREATE TABLE IF NOT EXISTS auth_pending_codes (
    code        TEXT PRIMARY KEY,      -- 4 位数字
    client_id   TEXT NOT NULL,
    created_at  TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    expires_at  TIMESTAMP NOT NULL,
    used        INTEGER DEFAULT 0
);
```

> **不需要 `auth_admins` 表**：管理员判定在 bot 侧用现成的 `_is_admin()`
> 完成（见 2.3）。后端只信任"带正确机器人 token 且声称已校验管理员"
> 的 `/auth/confirm` 请求。

### 3.2 后端接口

| 方法 | 路径 | 用途 | 鉴权方式 |
|---|---|---|---|
| POST | `/auth/request` | 网页申请验证码 | 无（任何人可申请，凭 client_id 隔离） |
| POST | `/auth/confirm` | **bot 调用**，用户私聊确认 | **机器人长期 token**（见 3.6） |
| GET  | `/auth/me` | 查询当前登录态 | 无（凭 client_id 查询） |
| POST | `/auth/logout` | 退出登录 | 需要登录态 |

**`/auth/request`**

```jsonc
// 请求
{ "client_id": "client_abc123" }
// 响应
{ "success": true, "code": "4821", "expires_in": 300 }
```

**`/auth/confirm`**（bot 调用）

```jsonc
// 请求头：Authorization: Bearer <BOT_TOKEN>
// 请求体
{ "code": "4821", "openid": "ABC123..." }
// 响应
{ "success": true, "message": "登录成功，请回到网页继续" }
// 失败
{ "success": false, "error": "验证码无效或已过期" }
```

> bot 用它与网页上传**同一个**长期 token，不再需要单独的共享密钥。
> bot 侧 `_is_admin()` 已确保"只有管理员能让验证码生效"。

用户**不会**直接拿到 token —— token 由后端写入 `auth_sessions`
（按 client_id），网页下次调用 `/auth/me` 时凭 client_id 换领 token
并存入 localStorage。这样避免把 token 通过 QQ 消息明文传递。

### 3.3 鉴权中间件

新增 `backend/app/auth.py`：

```python
def require_edit(client_id: str, token: str | None) -> None:
    """写操作依赖项：校验登录态，失败抛 401。"""
    # 1. token 为 None -> 401（前端据此 toast 提示 + 高亮登录按钮）
    # 2. sha256(token) 查 auth_sessions，匹配 client_id 且未过期 -> 通过
    # 3. 否则 401
```

在写接口上加依赖：

```python
@router.put("/{image_id}/tags")
async def update_image_tags(image_id: int, data: ImageUpdate,
                            auth: AuthContext = Depends(require_edit)):
    ...
```

#### 3.4.1 导入/导出接口：注释掉，不纳入鉴权

**决定：`/api/export`、`/api/export/all`、`/api/import`、`/api/import/all`
四个接口直接注释掉，不做鉴权改造。**

**理由**：JSON 导出导入在 45 万条数据量下本身就太慢，
实用性远不如直接备份 SQLite 数据库文件（`meme.db`，约 137 MB，复制即完成）。

| 方式 | 耗时量级 | 数据完整性 |
|---|---|---|
| JSON 导出/导入 | 慢到不可用 | 只含元数据，不含图片 |
| **直接备份 `meme.db`** | **秒级** | **完整** |

**实施方式**

1. 后端：把 `routers/system.py` 里这四个函数整体注释掉（保留代码备查），
   在注释处写明原因；
2. 前端：`FloatingButtons.vue` 的导出/导入按钮**暂时保留不变**
   （按需求"前端显示按钮暂时不变"）。

**⚠️ 必须处理的连带问题**：前端按钮保留但接口没了，点击会失败。
当前 `handleExport()` / `handleImport()` 会走 `systemApi.exportData()`，
接口注释掉后返回 404，用户看到的是"导出失败"。

**处理方案**（二选一，建议前者）：

- **加一条友好提示**：在 `handleExport` / `handleImport` 开头直接
  `toast.info('JSON 导入导出已停用，请直接备份 meme.db 数据库文件')` 并 return，
  不发请求；
- 或先接受点击报"导出失败"，后续再清理。

> 这样按钮外观不变（符合要求），但不会让用户等了很久才看到失败。

**导入功能作为鉴权前置条件的影响消除**

原方案把 `/import`、`/import/all` 列为最高危接口要重点保护。
废弃后，鉴权的必要性和复杂度都降低了 —— 这类"一键写全库"的入口本来就不该长期开放。

### 3.5 上传接口合并（不新增接口）

**现状：确实存在两个上传接口，实现几乎完全重复。**

| 接口 | 位置 | 调用方 |
|---|---|---|
| `POST /api/upload` | `main.py:579` | **网页**（`Gallery.vue:549`） |
| `POST /api/images/upload` | `images.py:233` | **机器人**（AstrBot 插件） |

两者的流程逐行相同：校验扩展名（按文件头）→ 算 MD5 → 查重 →
按分片落盘 → 生成缩略图 → 入库。这是一个纯粹的历史重复。

**处理方式：合并为 `POST /api/images/upload` 一个接口，删除 `/api/upload`。**

理由：
- 不再维护两份会逐渐分叉的实现；
- 前端只需改一行 URL（`Gallery.vue:549`）；
- 鉴权只需在一个地方加。

**迁移做法**

1. 把 `main.py:579` 的 `upload_file()` 删除；若担心外部调用方
   （如旧版本插件），可保留一个只做 301/内部转发的薄壳，标记 `deprecated`。
2. 前端 `Gallery.vue:549` 的 `/api/upload` → `/api/images/upload`。
3. 合并后确认两条路径的返回字段一致（现有注释已说明"返回字段与
   /api/images/upload 保持一致"，实际是同一套语义）。

### 3.6 机器人身份：手工配置长期账号

机器人**不用验证码登录**，改为在配置里给它一个长期身份。

**处理方式**

- 手工在数据库 `auth_sessions` 里插入一条长期有效的记录，
  绑定 `client_id = "bot"`（固定值，不走浏览器生成逻辑）；
- 机器人在上传请求头带：

  ```
  Authorization: Bearer <BOT_TOKEN>
  ```

- 该 token 有效期设为很长（如 10 年 / 不过期），且可随时删表记录吊销。

**配置方式**（二选一，建议前者）

```ini
# backend/.env 或环境变量
BQBQ_BOT_TOKEN=<一段足够长的随机串，至少 32 字符>
```

机器人插件侧在同一份配置里读同一个值（`_conf_schema.json` 新增一项）。

**好处**

- 不需要为 bot 单独开鉴权豁免分支 —— 它和网页走**同一套**中间件，
  只是 token 不同、永不过期；
- 少一个"特殊放行"的安全口子（原方案里的 `X-Bot-Secret` 豁免取消）；
- bot 侧改动极小：上传时多带一个请求头。

> **bot 调用的另一个接口** `GET /api/images/check-md5/{md5}` 是只读，
> 不需要鉴权，无需改动。

#### 3.7.2 登录流程：toast 引导，不弹窗

```
点击「QQ 登录」按钮
   ↓
POST /auth/request { client_id }  ->  { code: "4821" }
   ↓
toast.info('验证码 4821，请私聊机器人发送「bqbq登录 4821」，5 分钟内有效', 10000)
   ↓  按钮进入「等待确认」状态（旋转图标）
轮询 GET /auth/me（每 2 秒）
   ↓
成功 -> toast.success('登录成功') + 按钮变绿 + 圆点变绿
超时 -> toast.warning('验证码已过期，请重新点击登录')
```

**关键点**

- **验证码放在 toast 里显示**，不占用额外 UI。toast 已有 3 秒自动消失机制，
  这里传 `duration = 10000`（10 秒）保证能看清。
- **不新增弹窗组件** —— 验证码直接通过 toast 展示，登录全程不使用模态框。
- toast 消失后若还没确认，用户忘了验证码怎么办？——**再次点击登录按钮
  会重新申请**，旧码作废，新码再 toast 一次。不需要提供"查看当前验证码"。

#### 3.7.3 未登录时的 401 引导

任何写操作返回 401：

```
toast.warning('请先登录 QQ 再操作（点击右侧盾牌按钮）')
+ 登录按钮加一个脉冲高亮动画（如 animate-pulse，3 秒后移除）
```

**不使用弹窗，不阻断操作**，用户自己决定何时点。

#### 3.7.4 收起态（FAB 迷你条）不设登录入口

**明确：迷你条不新增登录按钮。** 登录入口只放在展开后的 FAB 网格里。

理由：

- 迷你条（`#fab-mini-strip`）定位是"常用快捷操作"（清空/刷新/搜索），
  塞入低频的登录会破坏它的简洁性；
- 收起态下用户本来就不方便做管理类操作，需要的自然会展开。

**但有一个体验问题要处理**：如果用户在收起状态下触发写操作收到 401，
toast 里必须告诉用户"先展开 FAB"，否则会找不到按钮：

```
toast.warning('请先登录：展开右侧悬浮按钮组，点击「QQ 登录」')
```

**轮询代价**：仅登录过程中轮询 `/auth/me`（间隔 2 秒，最多 5 分钟）。
日常使用零轮询。这是唯一新增的轮询，且生命周期很短。

## 四、延迟影响汇总

| 场景 | 现在 | 加鉴权后 | 变化 |
|---|---|---|---|
| 浏览/搜索/翻页 | 860ms × N | 860ms × N | **无变化** |
| 打标签 | 860ms | 860ms + 验签(~0) | **无感知** ✅ |
| 改规则 | 860ms | 860ms + 验签(~0) | **无感知** ✅ |
| 首次登录 | — | 一次 860ms（申请码） + QQ 消息 | 一次性 |
| Token 过期 | — | 同上 | 30 天才一次 |

**结论：不会让延迟翻倍。** 唯一新增的固定开销是登录那一次，
且可以做成长效（30 天）。

## 五、安全考虑

| 风险 | 对策 |
|---|---|
| 验证码被猜中 | 4 位 = 1 万种；有效期 5 分钟 + 每个 client_id 限次（如 5 次/小时）+ 用后即焚 |
| 验证码在 QQ 里被看到 | 私聊只有自己可见；且码只用于把 token 写进**发起请求的那个 client_id**，别人拿到码也没用（除非同时也控制了那个浏览器） |
| token 泄露 | 存 sha256 哈希；支持 `/auth/logout` 立即失效 |
| 库泄露 | 哈希后无法直接使用 |
| **机器人长期 token 泄露** | 单独一条记录、可随时删表吊销；token 只存在 bot 配置里，不经浏览器 |
| 非管理员冒充 | bot 侧用现成的 `_is_admin()` 把关（读 AstrBot 的 `role`），非管理员直接拒绝 |

**注意**：官方机器人拿到的是 **openid 而非 QQ 号**，所以任何 openid
比较都必须用 openid 形式（可用现有 `bqbq绑定` 命令让用户自查）。

**不再需要 `X-Bot-Secret` 豁免口子**：机器人改用长期 token 走同一套
鉴权中间件，少一个"特殊放行"分支就少一处可能写错的地方。

## 六、实施步骤（建议顺序）

| 步骤 | 内容 | 风险 |
|---|---|---|
| 1 | **注释掉导入/导出四个接口**；前端加"已停用"提示 | 低 |
| 2 | 建表 + `/auth/*` 接口 + `require_edit` 中间件 | 低（不影响现有功能） |
| 3 | **合并上传接口**：删 `/api/upload`，前端改调 `/api/images/upload` | 低 |
| 4 | 前端：token 管理 + FAB 登录按钮（替换 `#fab-import`）+ toast 引导 + 401 拦截 | 中 |
| 5 | bot：新增 `bqbq登录` 命令（供网页登录使用） | 低 |
| 6 | bot：上传时带长期 token（配置项） | 中 |
| 7 | 给写接口逐个加 `Depends(require_edit)` | **中（漏一个就是安全洞；多一个是功能中断）** |

**建议**：第 6、7 步之间务必先确认机器人配置好 token，否则开启后会全挂。
整体用一个开关 `BQBQ_AUTH_ENFORCE=0/1` 默认关闭，全过程验证无误后再打开。

## 八、备选简化方案（如果连 bot 改造都想省）

**纯验证码 + 网页直接确认**（不经 QQ）：

- 验证码在网页生成并显示，用户手工输入确认。
- **缺点**：没有第二因子，等于只加了"手势摩擦"，安全性提升有限。
- **优点**：零 bot 改动、零额外网络。

如果目的是"防止误操作"而非"防外部入侵"，这个方案够用；
如果是后者，必须走 QQ 确认。
