# 写操作登录鉴权方案（QQ 私聊验证码）

> 状态：**方案稿，尚未实施**
> 目标：所有写数据库的操作都需要登录态；尽量不增加公网链路延迟。

---

## 一、背景与现状核查

### 1.1 链路延迟实测（2026-10-23）

| 环节 | 实测值 |
|---|---|
| 本地后端响应（本机直连 8000） | 20 ~ 57 ms |
| 公网单次请求（经穿透到美国） | **860 ~ 970 ms** |
| 后端处理占比 | **不到 6%** |

结论：**延迟由请求数决定，不由单个请求的工作量决定。**
因此鉴权设计的第一原则是：**不要在每次写操作时增加网络往返。**

### 1.2 `bqbq_client_id` 现状

它在浏览器 `localStorage` 里生成（格式 `client_xxxxxxxxxxx`，见
`frontend/src/stores/useGlobalStore.ts:75-77`），唯一用途是作为
`client_id` 字段随请求回传。

**记录覆盖率（实测）**

| 接口 | 是否记录 client_id |
|---|---|
| 规则树 20 个写接口 | ✅ |
| `PUT /images/{id}/tags` | ✅ 调用记录 |
| `POST /images/upload` | ❌ |
| `DELETE /images/{id}` | ❌ |
| `POST /system/import`、`/import/all` | ❌（**接口已废弃，见 3.5.1**） |
| `GET /system/export`、`/export/all` | ❌（同上，已废弃） |

**`search_version_log` 实际数据**：仅 **64 条**，时间集中在
**2026-01-31 ~ 2026-02-04**（四天），4 个不同 client_id，此后完全空白。

**结论：`bqbq_client_id` 现在是匿名、可被用户任意清空的本机标识，
不能直接当身份体系。** 可以复用它作为"登录态载体"，但必须由后端
另行记录其权限状态，不能信任前端声明。

### 1.3 AstrBot 插件现状（关键约束）

`astrbot_plugin_bqbq_collect`：

| 事实 | 影响 |
|---|---|
| 纯**被动**接收（只有 `@filter.event_message_type` / `@filter.command`） | **无法主动发消息** |
| 没有任何 `send_message` / `context.send` 调用 | 同上 |
| 与后端同机，`backend_url = http://127.0.0.1:8000` | 通信延迟可忽略 ✅ |
| 已有 `@filter.command` 体系（如 `bqbq绑定`） | **加命令很容易** |

## 二、方案选型

### 2.1 为什么"每次写操作都问 bot"不可行

```
写标签 → 后端问 bot → bot 问 QQ → 用户确认 → 原路返回
        每次 ≈ 860ms × 多个往返
```
一次打标签可能要多等 2~3 秒。**排除。**

### 2.2 推荐方案：一次性验证码 + client_id 作为凭据

```
① 网页点「登录」→ POST /auth/request
        后端生成 4 位验证码，暂存 {code → client_id, 5 分钟过期}
        网页用 toast 展示验证码

② 用户在自己的 QQ 私聊 bot，发送：bqbq登录 1234
        插件收到命令 → POST /auth/confirm {code, sender_openid}
        后端校验 code 有效（不校验发送者身份）
        → 把该 client_id 写入 auth_granted_clients（永不过期）

③ 之后所有写请求照常带 client_id（现有接口已有该字段）
        后端查一次授权表（本机 SQLite，约 0.1ms）→ 通过/拒绝
```

**延迟影响**

| 操作 | 额外延迟 |
|---|---|
| 打标签 / 改规则 / 删除 | **≈ 0 ms** ✅（本机查表，无网络） |
| 登录（一次性） | 1 次 QQ 消息 + 本机 HTTP（< 1s） |
| 验证过期 | **不会过期**，验证一次永久有效 |

> **为什么延迟仍是 0**：授权校验是一次本机 SQLite 主键查询，
> 相比公网 RTT 860ms 完全可以忽略，且不产生任何网络往返。

### 2.3 Bot 侧改动量评估

**只需新增一个命令**，约 20 行，复用现有模式：

```python
@filter.command("bqbq登录", alias={"bqbq 登录", "bqbq认证"})
async def cmd_login(self, event: AstrMessageEvent):
    # 参数：event.message_str
    # 1. 取 4 位验证码
    # 2. 取 openid = event.get_sender_id()
    # 3. httpx POST 到 {backend}/auth/confirm
    # 4. 把后端返回的结果用 plain_result 回复
```

无需新增主动发消息能力 ✅

**不接 AstrBot 管理员名单**

按需求，**任何用户**私聊 bot 发验证码都能让自己的 client_id 生效，
不需要是 AstrBot 管理员。bot 侧因此**不需要 `_is_admin()` 校验**——
收到命令就直接转发给后端。

**这意味着什么（需知悉）**

| 场景 | 行为 |
|---|---|
| 你自己在网页申请验证码，私聊 bot 发送 | ✅ 登录成功 |
| 陌生人打开网站、自己申请验证码、自己私聊 bot | ⚠️ **也能登录成功并修改数据** |
| 有人猜到别人的 4 位码 | ⚠️ 若在有效期内抢先用掉，可能激活成功 |

**为什么这样仍然可用**

1. **验证码只显示在申请它的人自己的网页上**（通过 toast/面板），
   别人看不到；
2. 4 位码 + 5 分钟有效期 + 每个 client_id 限次 + 用后即焚，
   猜中且抢到的窗口极小；
3. 你的站点**本来就有 nginx 层 Basic 鉴权**挡在外面，
   陌生人到不了网页，自然也申请不到验证码。

> 若将来想收紧，只需在 bot 的 `cmd_login` 里加回一行
> `if not self._is_admin(event): return`，后端无需改动。
> 方案设计上保留了这条退路，但**默认不启用**。

## 三、详细设计

### 3.1 数据库表

```sql
-- 已授权的客户端（client_id 直接作为凭据，永不过期）
CREATE TABLE IF NOT EXISTS auth_granted_clients (
    client_id   TEXT PRIMARY KEY,      -- 浏览器 localStorage 里的 client_xxx
    openid      TEXT,                  -- 是谁完成验证的（审计 + 购物车按 openid 反查）
    granted_at  TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- 待确认的验证码（内存缓存即可，但落库便于重启后仍可用）
CREATE TABLE IF NOT EXISTS auth_pending_codes (
    code        TEXT PRIMARY KEY,      -- 4 位数字
    client_id   TEXT NOT NULL,
    created_at  TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    expires_at  TIMESTAMP NOT NULL,    -- 固定 5 分钟
    used        INTEGER DEFAULT 0
);

-- 操作审计日志（记录每一次写操作）
CREATE TABLE IF NOT EXISTS audit_log (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    client_id   TEXT NOT NULL,          -- 谁
    openid      TEXT,                   -- 对应 QQ 身份（可空）
    action      TEXT NOT NULL,          -- 什么操作：update_tags / delete_image / ...
    target      TEXT,                   -- 操作对象：image_id / group_id ...
    detail      TEXT,                   -- 变更内容摘要
    created_at  TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
CREATE INDEX IF NOT EXISTS idx_audit_created ON audit_log(created_at DESC);
CREATE INDEX IF NOT EXISTS idx_audit_client ON audit_log(client_id, created_at DESC);
```

**三级身份标识的关系**

| 层级 | 字段 | 用途 |
|---|---|---|
| 客户端 | `client_id` | 鉴权的**凭据**，区分不同浏览器 |
| **QQ 身份** | `openid` | 审计追责；购物车按 openid 反查（见购物车文档 6.1） |
| ~~管理员~~ | ~~AstrBot admins_id~~ | **不启用**：任何用户都能让验证码生效 |

> **不需要 token、哈希、过期时间字段** —— 详见 3.2 的设计说明。

### 3.2 凭据设计：client_id 直接当凭据

**结论：不签发 token，服务端只记录"哪些 client_id 已完成 QQ 验证"。**

**为什么这样够用**

| 威胁 | 是否被挡住 |
|---|---|
| 陌生人打开网站就能改数据 | ✅ 挡住。他有自己的 client_id，但不在授权表里 |
| 陌生人猜/撞 client_id | ✅ 几乎不可能（`client_` + 随机串） |
| 知道 client_id 的人拷到自己浏览器冒充 | ⚠️ 可以，但 client_id 只存在于本人 localStorage 与请求体中，不外露 |

**为什么不引入 token**：token 唯一实质收益就是防住"client_id 被主动泄露"这一个窄场景，
代价却是要新增签发、哈希存储、请求头传递、验签、过期判断、退出清理一整套。

**放弃 token 的代价（需接受）**

- 无独立吊销机制：要注销某个客户端，直接删 `auth_granted_clients` 那一行；
- 无自动过期：验证一次永久有效（按需求设定）；
- 清空浏览器数据后 client_id 会重新生成，**需要重新完成一次 QQ 验证**。

### 3.3 后端接口

| 方法 | 路径 | 用途 | 鉴权方式 |
|---|---|---|---|
| POST | `/auth/request` | 网页申请验证码 | 无（任何人可申请） |
| POST | `/auth/confirm` | **bot 调用**，用户私聊确认 | 本轮**不加鉴权**（见下方说明） |
| GET  | `/auth/me` | 查询当前登录态 | 无（凭 client_id 查询） |
| POST | `/auth/logout` | 退出登录 | 需要已授权 |

**`/auth/request`**

```jsonc
// 请求
{ "client_id": "client_abc123" }
// 响应
{ "success": true, "code": "4821", "expires_in": 300 }
```

**`/auth/confirm`**（bot 调用）

```jsonc
// 请求体
{ "code": "4821", "openid": "ABC123..." }
// 响应
{ "success": true, "message": "登录成功，请回到网页继续" }
// 失败
{ "success": false, "error": "验证码无效或已过期" }
```

> **本轮该接口不加鉴权**（bot 代码一行不改）。
> 安全性依赖两点：① 验证码是 4 位一次性、5 分钟过期、用后即焚；
> ② 验证码只显示在申请人自己的网页上，别人看不到。
> ③ 站点本身有 nginx Basic 鉴权，陌生人进不了网页。
>
> 若要再加一层保险又不改 bot：可校验调用来源必须是 `127.0.0.1`
> （bot 与后端同机，见 1.3 节）。

**`/auth/me`**

```jsonc
// 请求：GET /auth/me?client_id=client_abc123
// 响应
{ "granted": true }
// 或
{ "granted": false }
```

网页登录后凭 client_id 查一次即可知道状态，**不涉及任何 token 交换**。

### 3.4 鉴权中间件

新增 `backend/app/auth.py`：

```python
def require_edit(client_id: str) -> None:
    """写操作依赖项：校验该 client_id 是否已完成 QQ 验证。"""
    # 1. client_id 为空 -> 401
    # 2. 查 auth_granted_clients，存在 -> 通过
    # 3. 不存在 -> 401（前端据此 toast 提示 + 高亮登录按钮）
```

在写接口上加依赖：

```python
@router.put("/{image_id}/tags")
async def update_image_tags(image_id: int, data: ImageUpdate,
                            _: None = Depends(require_edit)):
    ...
```

#### 3.4.1 client_id 从哪里取（各接口不同）

**核心原则：优先用"现有请求里本来就有 client_id"的位置，避免让调用方改动。**

| 接口类型 | 携带方式 | 网页要改吗 | bot 要改吗 |
|---|---|---|---|
| 规则树 20 个写接口 | **请求体 JSON 字段** `client_id` | ❌ **不用改**（本来就有） | — |
| `PUT /images/{id}/tags` | **请求体 JSON 字段** | ❌ 不用改 | — |
| `DELETE /images/{id}` | **请求体 JSON 字段** | ❌ 不用改 | — |
| `POST /system/update_tags` | **请求体 JSON 字段** | ❌ 不用改 | — |
| `POST /api/upload`（网页上传） | **URL query** `?client_id=` | ✅ 改 1 行 URL | — |
| `POST /api/images/upload`（bot） | **URL query** | — | ✅ 改 URL 常量 |

**为什么两个上传接口要用 URL 参数**：它们只接收 multipart 文件
（`file: UploadFile`），**没有 JSON 请求体**，client_id 无处安放。

**为什么网页其它接口不用改**：`useApi.ts` 里 20 多个写方法已经在发
`client_id` 字段了（`clientId: string` 参数），后端直接从请求体取即可。

> 结论：**网页只有上传函数需要改一行 URL**，其余 20+ 个写接口零改动。

### 3.5 需要加鉴权的接口清单

**所有写接口都要加鉴权**，包括 bot 用的上传接口。

| 文件 | 接口 | 调用方 | client_id 来源 |
|---|---|---|---|
| `main.py` | `POST /api/upload` | 网页 | 请求体 / query |
| `routers/images.py` | `POST /images/upload` | **bot** | **query** |
| `routers/images.py` | `POST /images`（新建记录） | 网页 | 请求体 |
| `routers/images.py` | `PUT /images/{id}/tags` | 网页 | 请求体 |
| `routers/images.py` | `DELETE /images/{id}` | 网页 | 请求体 |
| `routers/rules.py` | 全部 20 个写接口 | 网页 | 请求体 |
| `routers/system.py` | `POST /system/update_tags` | 网页 | 请求体 |

> 表格里的 `routers/images.py` 路径实际前缀是 `/api/images/`。

**导入/导出接口已废弃，不在鉴权范围内** —— 见 3.5.1。

**只读接口（搜索、列表、缩略图、规则读取、`check-md5`）不加鉴权** ——
否则每次翻页都要验证，在网络差时会很难受。

#### 3.5.1 导入/导出接口：注释掉，不纳入鉴权

**决定：`/api/export`、`/api/export/all`、`/api/import`、`/api/import/all`
四个接口直接注释掉，不做鉴权改造。**

**理由**：JSON 导出导入在 45 万条数据量下本身就太慢，
实用性远不如直接备份 SQLite 数据库文件（`meme.db`，约 137 MB，复制即完成）。

| 方式 | 耗时量级 | 数据完整性 |
|---|---|---|
| JSON 导出/导入 | 慢到不可用 | 只含元数据，不含图片 |
| **直接备份 `meme.db`** | **秒级** | **完整** |

**实施方式**

1. 后端：把 `routers/system.py` 里这四个函数整体注释掉（保留代码备查），
   在注释处写明原因；
2. 前端：`FloatingButtons.vue` 的导出/导入按钮**暂时保留不变**
   （按需求"前端显示按钮暂时不变"）。

**⚠️ 必须处理的连带问题**：前端按钮保留但接口没了，点击会失败。
当前 `handleExport()` / `handleImport()` 会走 `systemApi.exportData()`，
接口注释掉后返回 404，用户看到的是"导出失败"。

**处理方案**（二选一，建议前者）：

- **加一条友好提示**：在 `handleExport` / `handleImport` 开头直接
  `toast.info('JSON 导入导出已停用，请直接备份 meme.db 数据库文件')` 并 return，
  不发请求；
- 或先接受点击报"导出失败"，后续再清理。

> 这样按钮外观不变（符合要求），但不会让用户等了很久才看到失败。

**导入功能废弃对鉴权的影响**

导入曾经是"一键写全库"的最高危入口，需要重点保护。
废弃后，鉴权的必要性和复杂度都降低了 —— 这类批量写库的入口
本来就不该长期对外开放。

### 3.6 上传接口：本轮不合并，仅给网页入口加鉴权

**现状核对（实测两个 bot 插件）**：确实有两个上传接口，但调用方完全分离。

| 接口 | 位置 | 调用方 |
|---|---|---|
| `POST /api/upload` | `main.py:579` | **仅网页**（`Gallery.vue:549`） |
| `POST /api/images/upload` | `images.py:233` | **仅机器人** |

**两个 bot 实际使用的接口（逐一核对）**

nonebot2 插件（`__init__.py`）—— 只用了 2 个：

| 接口 | 用途 |
|---|---|
| `POST /api/images/upload` | 上传 |
| `GET /api/images/check-md5/{md5}` | 查重（只读） |

AstrBot 插件（`main.py` + `imagelib.py`）—— 用了 5 个：

| 接口 | 用途 | 备注 |
|---|---|---|
| `POST /api/images/upload` | 上传 | 写 |
| `GET /api/images/check-md5/{md5}` | 查重 | 只读 |
| `POST /api/search` | 搜索 | 只读 |
| `GET /{kind}/{rel}` | 取图/缩略图 | 只读 |
| `POST /api/update_tags` | 改标签 | 写，但**有定义无调用**（死代码） |

**关键结论：两个 bot 都没有使用网页的 `/api/upload`。**

**本轮做法：不合并，两边各管各的。**

| 接口 | 本轮处理 |
|---|---|
| `POST /api/upload`（网页） | **加 `require_edit` 鉴权** |
| `POST /api/images/upload`（bot） | **加 `require_edit` 鉴权**（bot 需带 client_id） |

**理由**

- 两个接口调用方零重叠，**合并不是鉴权的前提**，所以本轮不合并；
- 但两个接口**都要加鉴权** —— 统一用同一套 client_id 逻辑；
- bot 只需改一行 URL 常量即可带上 client_id（见 3.7）。

**后续（下一轮再合并）**

合并为 `POST /api/images/upload` 一个接口，届时：

1. 改前端 `Gallery.vue:549`；
2. 删除 `main.py:579` 的 `upload_file()`。

> 合并只是消除重复实现，与鉴权无关。

### 3.7 机器人身份：与网页同一套 client_id

**机器人不使用任何 token，只用 `client_id`，手工添加即可。**

**做法**

1. 给两个 bot 各指定一个固定 client_id：
   · nonebot2 -> `bot_nonebot`
   · AstrBot   -> `bot_astrbot`
2. 手工把它插入授权表：

```sql
INSERT INTO auth_granted_clients (client_id, openid) VALUES
  ('bot_nonebot', 'manual'),
  ('bot_astrbot', 'manual');
```

3. bot 上传时在 URL 上带 query 参数：

```
POST /api/images/upload?client_id=bot_astrbot     （AstrBot）
POST /api/images/upload?client_id=bot_nonebot     （nonebot2）
```

**为什么用 query 参数（而不是请求头或 form 字段）**

两个上传接口目前**只接收 multipart 文件**，请求体里没有 client_id。
三种携带方式的改动量：

| 方式 | nonebot2 | AstrBot | 说明 |
|---|---|---|---|
| **URL query（采用）** | 改 `UPLOAD_API` 常量 1 处 | 改 2 处 URL 字符串 | **最小** |
| 请求头 `X-Client-Id` | 改 `client.post` 调用 | 改 2 处调用 | 多一处改动 |
| form 字段 | 需改 files/data 混合写法 | 同左 | 最容易写错 |

nonebot2 侧尤其干净 —— `UPLOAD_API` 是模块级常量（`__init__.py:29`）：

```python
BOT_CLIENT_ID = "bot_nonebot"
UPLOAD_API = f"{BACKEND_BASE_URL}/api/images/upload?client_id={BOT_CLIENT_ID}"
```

AstrBot 侧改两个字符串即可（`main.py:704`、`imagelib.py:463`）：

```python
BOT_CLIENT_ID = "bot_astrbot"
f"{self.backend}/api/images/upload?client_id={BOT_CLIENT_ID}"
```

**两个 bot 用不同的 client_id**

| bot | client_id | 用途 |
|---|---|---|
| nonebot2 | `bot_nonebot` | 便于在授权表与日志里区分来源 |
| AstrBot | `bot_astrbot` | 同上 |

各自在授权表插入一条：

```sql
INSERT INTO auth_granted_clients (client_id, openid) VALUES
  ('bot_nonebot', 'manual'),
  ('bot_astrbot', 'manual');
```

**好处**：出问题时能一眼看出是哪路 bot 上传的；要停用某一路，
只删它那一行即可，不影响另一路。

**安全性说明**

client_id 出现在 URL 里会被 nginx 访问日志记录 —— 这**没有安全影响**，
因为按本方案 client_id 从不是秘密（网页请求体里本来就带着它），
安全性完全由服务端授权表保证。

**后端如何接收**

```python
@router.post("/upload")
async def upload_image(file: UploadFile = File(...),
                       client_id: str | None = None,
                       _: None = Depends(require_edit)):
    ...
```

FastAPI 会自动从 query 参数解析 `client_id`。

> **bot 调用的另一个接口** `GET /api/images/check-md5/{md5}` 是只读，
> 不需要鉴权，无需改动。

#### 3.8.3 登录流程

```
点击「QQ 登录」按钮（或面板内「获取验证码」）
   ↓
POST /auth/request { client_id }  ->  { code: "4821", expires_in: 300 }
   ↓
面板显示「bqbq登录 4821」+ 倒计时
   ↓
用户私聊 bot 发送该指令 → bot 调 /auth/confirm
   ↓  按钮进入「等待确认」状态（图标轻微脉冲）
轮询 GET /auth/me（每 2 秒，最多 5 分钟）
   ↓
成功 -> toast.success('登录成功') + 图标由灰转青 + 面板切到已登录态
超时 -> 面板显示「已过期，请点『换一个验证码』」
```

**轮询代价**：仅登录过程中轮询（2 秒间隔，最长 5 分钟）。
日常使用零轮询。

#### 3.8.4 未登录时的 401 引导

任何写操作返回 401：

```
toast.warning('请先登录 QQ 再操作（点击右侧盾牌按钮）')
+ 登录按钮加一个脉冲高亮动画（如 animate-pulse，3 秒后移除）
```

**不弹模态框，不阻断操作**，用户自己决定何时点。

#### 3.8.5 收起态（FAB 迷你条）不设登录入口

**明确：迷你条不新增登录按钮。** 登录入口只放在展开后的 FAB 网格里。

理由：

- 迷你条（`#fab-mini-strip`）定位是"常用快捷操作"（清空/刷新/搜索），
  塞入低频的登录会破坏它的简洁性；
- 收起态下用户本来就不方便做管理类操作，需要的自然会展开。

**但有一个体验问题要处理**：如果用户在收起状态下触发写操作收到 401，
toast 里必须告诉用户"先展开 FAB"，否则会找不到按钮：

```
toast.warning('请先登录：展开右侧悬浮按钮组，点击「QQ 登录」')
```

**轮询代价**：仅登录过程中轮询 `/auth/me`（间隔 2 秒，最多 5 分钟）。
日常使用零轮询。这是唯一新增的轮询，且生命周期很短。

## 四、延迟影响汇总

| 场景 | 现在 | 加鉴权后 | 变化 |
|---|---|---|---|
| 浏览/搜索/翻页 | 860ms × N | 860ms × N | **无变化**（只读不校验） |
| 打标签 | 860ms | 860ms + 查表(~0.1ms) | **无感知** ✅ |
| 改规则 | 860ms | 860ms + 查表(~0.1ms) | **无感知** ✅ |
| 首次登录 | — | 一次 860ms（申请码） + QQ 消息 | 一次性 |
| 有效期 | — | **永不过期** | 验证一次长期有效 |

**结论：不会让延迟翻倍。** 写操作只多一次本机 SQLite 主键查询，
唯一新增的固定开销是首次登录那一次。

## 五、安全考虑

| 风险 | 对策 |
|---|---|
| 陌生人打开网站就想改数据 | 他的 client_id 不在 `auth_granted_clients` 表里 → 401 |
| 验证码被猜中 | 4 位 = 1 万种；有效期 5 分钟 + 每个 client_id 限次（如 5 次/小时）+ 用后即焚 |
| 验证码在 QQ 里被看到 | 私聊只有自己可见；且码只用于把**发起请求的那个 client_id** 写进授权表，别人拿到码也没用（除非同时控制了那个浏览器） |
| 知道他人 client_id 并拷到自己浏览器 | ⚠️ 理论上可冒用。但 client_id 只存在于本人 localStorage 与请求体中，不外露；真要注销，删授权表那一行即可 |
| **机器人 client_id 泄露** | client_id 出现在上传 URL 里（可能被 nginx 日志记录）。影响有限：它能上传图片，但不能改规则树/删图（那些接口同样要校验，且 client_id 相同）。真要吊销，删授权表那一行 |
| 陌生人自助登录 | 他需要先能打开网页拿到验证码（nginx Basic 鉴权已挡）；且验证码 5 分钟过期、用后即焚 |

**注意**：官方机器人拿到的是 **openid 而非 QQ 号**，所以任何 openid
比较都必须用 openid 形式（可用现有 `bqbq绑定` 命令让用户自查）。

**统一的凭据模型：全部用 client_id**

| 主体 | client_id 来源 | 如何获得授权 |
|---|---|---|
| 网页浏览器 | 浏览器 localStorage 自动生成 | 走 QQ 验证码流程 |
| 机器人（两个） | **手工指定固定值**：`bot_nonebot` / `bot_astrbot` | **手工插入授权表** |

两边走**完全相同**的 `require_edit` 逻辑，区别只是 client_id 从哪来：

| 主体 | 后端从哪取 client_id |
|---|---|
| 网页 | 请求体 JSON 的 `client_id` 字段 |
| 机器人上传 | **URL query 参数** `?client_id=...` |

**不引入任何 token、密钥、环境变量。**

## 五点一、操作审计

**已确认要做。** 记录每一次写操作，便于回溯"谁在什么时候改了什么"。

### 记录什么

| 字段 | 内容 | 来源 |
|---|---|---|
| `client_id` | 谁 | 鉴权参数 |
| `openid` | 对应 QQ 身份 | 从 `auth_granted_clients` 反查 |
| `action` | 什么操作 | `update_tags` / `delete_image` / `create_group` ... |
| `target` | 操作对象 | `image_id=123` / `group_id=45` |
| `detail` | 变更摘要 | 如 `tags: "猫 可爱" -> "猫"` |
| `created_at` | 时间 | 自动 |

### 怎么写（避免污染业务代码）

用**装饰器或依赖注入**统一写，不要在每个接口里手写 INSERT：

```python
# backend/app/audit.py
def audit(action: str):
    """在写接口上标记操作名，由中间件统一记录。"""
    def decorator(fn):
        fn.__audit_action__ = action
        return fn
    return decorator
```

```python
@router.put("/{image_id}/tags")
@audit("update_tags")
async def update_image_tags(image_id: int, data: ImageUpdate, ...):
    ...
```

**关键的取舍：只记录"成功"的操作**

- 中间件在响应 200 时才写入审计
- 失败（401/400/500）不记，避免日志被无效请求淹没

### 与现有 `search_version_log` 的关系

| 表 | 覆盖范围 | 处理 |
|---|---|---|
| `search_version_log` | 规则树 20 个写接口 | **保留不动**（它还承担版本号递增职责） |
| `audit_log` | **全部写接口** | 新增，作为统一审计 |

> 两张表会有部分重叠（规则树的写操作两处都记）。这是可接受的——
> `search_version_log` 服务版本控制，`audit_log` 服务审计，语义不同。

### 清理策略

审计日志会持续增长。建议：

```sql
-- 保留最近 90 天
DELETE FROM audit_log WHERE created_at < datetime('now', '-90 days');
```

可在现有的 15 分钟定时任务里顺带执行（每月真正删一次即可，成本可忽略）。

### 查询入口（可选，后续再加）

初期**不做管理界面**，需要时直接查 SQL：

```sql
SELECT * FROM audit_log ORDER BY id DESC LIMIT 100;
SELECT * FROM audit_log WHERE client_id = 'xxx' ORDER BY id DESC;
```

## 八、备选简化方案（如果连 bot 改造都想省）

**纯验证码 + 网页直接确认**（不经 QQ）：

- 验证码在网页生成并显示，用户手工输入确认。
- **缺点**：没有第二因子，等于只加了"手势摩擦"，安全性提升有限。
- **优点**：零 bot 改动、零额外网络。

如果目的是"防止误操作"而非"防外部入侵"，这个方案够用；
如果是后者，必须走 QQ 确认。

## 九、已确定的决策

以下为评审后落定的关键决策，实施时以此为准：

| 决策项 | 结论 |
|---|---|
| **登录态 UI** | FAB 网格里的 `#fab-import` 改造为 QQ 登录按钮 |
| **登录按钮图标** | **手绘企鹅轮廓线**（`stroke-width=2`，与全部 FAB 按钮同风格） |
| **验证码展示** | **登录面板 `#login-panel`**（仿 `#tag-count-panel`），持续可见 + 倒计时；不用 toast（太短） |
| **FAB 按钮总数** | 保持 **10 个**（替换而非新增） |
| **登录态区分** | **仅用图标颜色**：未登录 `text-slate-400`(灰) / 已登录 `text-cyan-600`(青)。**不加圆点** |
| **图标尺寸** | **`w-7 h-7`（28px）**，与 `#fab-upload` 同大，比导出/排序大一号 |
| **凭据模型** | **全部统一用 `client_id`**，不引入任何 token / 密钥 / 环境变量 |
| **网页凭据** | 浏览器自动生成，授权表记录；**永不过期** |
| **网页携带方式** | **请求体 `client_id` 字段**（现有接口已有，20+ 接口零改动） |
| **网页上传** | 无请求体 → **URL query** `?client_id=`（唯一需改的网页接口） |
| **机器人凭据** | 手工指定固定 client_id 并插入授权表；上传 URL 带 `?client_id=` |
| **两个 bot 的 client_id** | **各用一个值**：`bot_nonebot` / `bot_astrbot`，便于区分来源 |
| **管理员名单** | **不做**。任何用户私聊 bot 发验证码都能让 client_id 生效 |
| **操作审计** | **要做**，新增 `audit_log` 表 + `@audit()` 装饰器（见第五章之一） |
| **导出按钮** | 前端**保持原样不改**；后端接口注释掉（购物车方案会再动它） |
| **导入按钮** | 被登录按钮取代（接口已废弃） |
| **收起态迷你条** | **不设**登录入口 |
| **两个上传接口** | **本轮不合并**，但**两个都加鉴权** |
| **导入导出接口** | 全部注释掉，改用直接备份 `meme.db` |
| **登录态校验方式** | 本机查一次授权表（~0.1ms），**不产生网络往返** |
