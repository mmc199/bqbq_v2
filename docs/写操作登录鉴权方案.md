# 写操作登录鉴权方案（QQ 私聊验证码）

> 状态：**方案稿，尚未实施**
> 目标：所有写数据库的操作都需要登录态；尽量不增加公网链路延迟。

---

## 一、背景与现状核查

### 1.1 链路延迟实测（2026-10-23）

| 环节 | 实测值 |
|---|---|
| 本地后端响应（本机直连 8000） | 20 ~ 57 ms |
| 公网单次请求（经穿透到美国） | **860 ~ 970 ms** |
| 后端处理占比 | **不到 6%** |

结论：**延迟由请求数决定，不由单个请求的工作量决定。**
因此鉴权设计的第一原则是：**不要在每次写操作时增加网络往返。**

### 1.2 `bqbq_client_id` 现状

它在浏览器 `localStorage` 里生成（格式 `client_xxxxxxxxxxx`，见
`frontend/src/stores/useGlobalStore.ts:75-77`），唯一用途是作为
`client_id` 字段随请求回传。

**记录覆盖率（实测）**

| 接口 | 是否记录 client_id |
|---|---|
| 规则树 20 个写接口 | ✅ |
| `PUT /images/{id}/tags` | ✅ 调用记录 |
| `POST /images/upload` | ❌ |
| `DELETE /images/{id}` | ❌ |
| `POST /images/upload` | ❌ |
| `DELETE /images/{id}` | ❌ |
| `POST /system/import`、`/import/all` | ❌（**接口已废弃，见 3.4.1**） |
| `GET /system/export`、`/export/all` | ❌（同上，已废弃） |

**`search_version_log` 实际数据**：仅 **64 条**，时间集中在
**2026-01-31 ~ 2026-02-04**（四天），4 个不同 client_id，此后完全空白。

**结论：`bqbq_client_id` 现在是匿名、可被用户任意清空的本机标识，
不能直接当身份体系。** 可以复用它作为"登录态载体"，但必须由后端
另行记录其权限状态，不能信任前端声明。

### 1.3 AstrBot 插件现状（关键约束）

`astrbot_plugin_bqbq_collect`：

| 事实 | 影响 |
|---|---|
| 纯**被动**接收（只有 `@filter.event_message_type` / `@filter.command`） | **无法主动发消息** |
| 没有任何 `send_message` / `context.send` 调用 | 同上 |
| 与后端同机，`backend_url = http://127.0.0.1:8000` | 通信延迟可忽略 ✅ |
| 已有 `@filter.command` 体系（如 `bqbq绑定`） | **加命令很容易** |

## 二、方案选型

### 2.1 为什么"每次写操作都问 bot"不可行

```
写标签 → 后端问 bot → bot 问 QQ → 用户确认 → 原路返回
        每次 ≈ 860ms × 多个往返
```
一次打标签可能要多等 2~3 秒。**排除。**

### 2.2 推荐方案：一次性验证码 + client_id 作为凭据

```
① 网页点「登录」→ POST /auth/request
        后端生成 4 位验证码，暂存 {code → client_id, 5 分钟过期}
        网页用 toast 展示验证码

② 用户在自己的 QQ 私聊 bot，发送：bqbq登录 1234
        插件收到命令 → POST /auth/confirm {code, sender_openid}
        后端校验 code 有效 + 发送者是管理员
        → 把该 client_id 写入 auth_granted_clients（永不过期）

③ 之后所有写请求照常带 client_id（现有接口已有该字段）
        后端查一次授权表（本机 SQLite，约 0.1ms）→ 通过/拒绝
```

**延迟影响**

| 操作 | 额外延迟 |
|---|---|
| 打标签 / 改规则 / 删除 | **≈ 0 ms** ✅（本机查表，无网络） |
| 登录（一次性） | 1 次 QQ 消息 + 本机 HTTP（< 1s） |
| 验证过期 | **不会过期**，验证一次永久有效 |

> **为什么延迟仍是 0**：授权校验是一次本机 SQLite 主键查询，
> 相比公网 RTT 860ms 完全可以忽略，且不产生任何网络往返。

### 2.3 Bot 侧改动量评估

**只需新增一个命令**，约 20 行，复用现有模式：

```python
@filter.command("bqbq登录", alias={"bqbq 登录", "bqbq认证"})
async def cmd_login(self, event: AstrMessageEvent):
    # 参数：event.message_str
    # 1. 取 4 位验证码
    # 2. 取 openid = event.get_sender_id()
    # 3. httpx POST 到 {backend}/auth/confirm
    # 4. 把后端返回的结果用 plain_result 回复
```

无需新增主动发消息能力 ✅

**管理员判定可直接复用现有设施**：插件里已有
`_is_admin(event)`（`main.py:1371`），它读 AstrBot 在事件上设好的
`role` 字段（由 AstrBot 的 `admins_id` 配置决定）。

**因此不需要自建 `auth_admins` 表** —— 管理员身份在 bot 侧判定，
bot 只把"已通过管理员校验"的确认转发给后端即可。这比让后端
维护 openid 名单更简单，也和现有代码一致。

## 三、详细设计

### 3.1 数据库表

```sql
-- 已授权的客户端（client_id 直接作为凭据，永不过期）
CREATE TABLE IF NOT EXISTS auth_granted_clients (
    client_id   TEXT PRIMARY KEY,      -- 浏览器 localStorage 里的 client_xxx
    openid      TEXT,                  -- 是谁完成验证的（便于追溯）
    granted_at  TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- 待确认的验证码（内存缓存即可，但落库便于重启后仍可用）
CREATE TABLE IF NOT EXISTS auth_pending_codes (
    code        TEXT PRIMARY KEY,      -- 4 位数字
    client_id   TEXT NOT NULL,
    created_at  TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    expires_at  TIMESTAMP NOT NULL,    -- 固定 5 分钟
    used        INTEGER DEFAULT 0
);
```

> **不需要 token、哈希、过期时间字段** —— 详见 3.2 的设计说明。

### 3.2 凭据设计：client_id 直接当凭据

**结论：不签发 token，服务端只记录"哪些 client_id 已完成 QQ 验证"。**

**为什么这样够用**

| 威胁 | 是否被挡住 |
|---|---|
| 陌生人打开网站就能改数据 | ✅ 挡住。他有自己的 client_id，但不在授权表里 |
| 陌生人猜/撞 client_id | ✅ 几乎不可能（`client_` + 随机串） |
| 知道 client_id 的人拷到自己浏览器冒充 | ⚠️ 可以，但 client_id 只存在于本人 localStorage 与请求体中，不外露 |

**为什么不引入 token**：token 唯一实质收益就是防住"client_id 被主动泄露"这一个窄场景，
代价却是要新增签发、哈希存储、请求头传递、验签、过期判断、退出清理一整套。

**放弃 token 的代价（需接受）**

- 无独立吊销机制：要注销某个客户端，直接删 `auth_granted_clients` 那一行；
- 无自动过期：验证一次永久有效（按需求设定）；
- 清空浏览器数据后 client_id 会重新生成，**需要重新完成一次 QQ 验证**。

### 3.3 后端接口

| 方法 | 路径 | 用途 | 鉴权方式 |
|---|---|---|---|
| POST | `/auth/request` | 网页申请验证码 | 无（任何人可申请） |
| POST | `/auth/confirm` | **bot 调用**，用户私聊确认 | 本轮**不加鉴权**（见下方说明） |
| GET  | `/auth/me` | 查询当前登录态 | 无（凭 client_id 查询） |
| POST | `/auth/logout` | 退出登录 | 需要已授权 |

**`/auth/request`**

```jsonc
// 请求
{ "client_id": "client_abc123" }
// 响应
{ "success": true, "code": "4821", "expires_in": 300 }
```

**`/auth/confirm`**（bot 调用）

```jsonc
// 请求体
{ "code": "4821", "openid": "ABC123..." }
// 响应
{ "success": true, "message": "登录成功，请回到网页继续" }
// 失败
{ "success": false, "error": "验证码无效或已过期" }
```

> **本轮该接口不加鉴权**（bot 代码一行不改）。
> 安全性依赖两点：① 验证码是 4 位一次性、5 分钟过期、用后即焚；
> ② bot 侧 `_is_admin()` 已确保只有管理员能让验证码生效。
>
> 若要再加一层保险又不改 bot：可校验调用来源必须是 `127.0.0.1`
> （bot 与后端同机，见 1.3 节）。

**`/auth/me`**

```jsonc
// 请求：GET /auth/me?client_id=client_abc123
// 响应
{ "granted": true }
// 或
{ "granted": false }
```

网页登录后凭 client_id 查一次即可知道状态，**不涉及任何 token 交换**。

### 3.4 鉴权中间件

新增 `backend/app/auth.py`：

```python
def require_edit(client_id: str) -> None:
    """写操作依赖项：校验该 client_id 是否已完成 QQ 验证。"""
    # 1. client_id 为空 -> 401
    # 2. 查 auth_granted_clients，存在 -> 通过
    # 3. 不存在 -> 401（前端据此 toast 提示 + 高亮登录按钮）
```

在写接口上加依赖：

```python
@router.put("/{image_id}/tags")
async def update_image_tags(image_id: int, data: ImageUpdate,
                            _: None = Depends(require_edit)):
    ...
```

**注意**：`require_edit` 从请求体里取 `client_id`（现有接口已有该字段），
不需要额外请求头。

### 3.5 需要加鉴权的接口清单

**本轮只给网站用的写接口加鉴权，bot 专用接口保持原样。**

| 文件 | 接口 | 调用方 | 本轮处理 |
|---|---|---|---|
| `main.py` | `POST /api/upload` | 仅网页 | ✅ **加鉴权** |
| `routers/images.py` | `POST /images`（新建记录） | 仅网页 | ✅ 加鉴权 |
| `routers/images.py` | `PUT /images/{id}/tags` | 仅网页 | ✅ 加鉴权 |
| `routers/images.py` | `DELETE /images/{id}` | 仅网页 | ✅ 加鉴权 |
| `routers/rules.py` | 全部 20 个写接口 | 仅网页 | ✅ 加鉴权 |
| `routers/system.py` | `POST /system/update_tags` | 仅网页 | ✅ 加鉴权 |
| `routers/images.py` | `POST /images/upload` | **仅 bot** | ⏸️ **本轮不动** |

> 表格里的 `routers/images.py` 路径实际前缀是 `/api/images/`。
> `/api/images/upload` 本轮不加鉴权，下一轮合并接口时再处理（见 3.6）。

**导入/导出接口已废弃，不在鉴权范围内** —— 见 3.5.1。

**只读接口（搜索、列表、缩略图、规则读取、`check-md5`）不加鉴权** ——
否则每次翻页都要验证，在网络差时会很难受。

#### 3.5.1 导入/导出接口：注释掉，不纳入鉴权

**决定：`/api/export`、`/api/export/all`、`/api/import`、`/api/import/all`
四个接口直接注释掉，不做鉴权改造。**

**理由**：JSON 导出导入在 45 万条数据量下本身就太慢，
实用性远不如直接备份 SQLite 数据库文件（`meme.db`，约 137 MB，复制即完成）。

| 方式 | 耗时量级 | 数据完整性 |
|---|---|---|
| JSON 导出/导入 | 慢到不可用 | 只含元数据，不含图片 |
| **直接备份 `meme.db`** | **秒级** | **完整** |

**实施方式**

1. 后端：把 `routers/system.py` 里这四个函数整体注释掉（保留代码备查），
   在注释处写明原因；
2. 前端：`FloatingButtons.vue` 的导出/导入按钮**暂时保留不变**
   （按需求"前端显示按钮暂时不变"）。

**⚠️ 必须处理的连带问题**：前端按钮保留但接口没了，点击会失败。
当前 `handleExport()` / `handleImport()` 会走 `systemApi.exportData()`，
接口注释掉后返回 404，用户看到的是"导出失败"。

**处理方案**（二选一，建议前者）：

- **加一条友好提示**：在 `handleExport` / `handleImport` 开头直接
  `toast.info('JSON 导入导出已停用，请直接备份 meme.db 数据库文件')` 并 return，
  不发请求；
- 或先接受点击报"导出失败"，后续再清理。

> 这样按钮外观不变（符合要求），但不会让用户等了很久才看到失败。

**导入功能废弃对鉴权的影响**

导入曾经是"一键写全库"的最高危入口，需要重点保护。
废弃后，鉴权的必要性和复杂度都降低了 —— 这类批量写库的入口
本来就不该长期对外开放。

### 3.6 上传接口：本轮不合并，仅给网页入口加鉴权

**现状核对（实测两个 bot 插件）**：确实有两个上传接口，但调用方完全分离。

| 接口 | 位置 | 调用方 |
|---|---|---|
| `POST /api/upload` | `main.py:579` | **仅网页**（`Gallery.vue:549`） |
| `POST /api/images/upload` | `images.py:233` | **仅机器人** |

**两个 bot 实际使用的接口（逐一核对）**

nonebot2 插件（`__init__.py`）—— 只用了 2 个：

| 接口 | 用途 |
|---|---|
| `POST /api/images/upload` | 上传 |
| `GET /api/images/check-md5/{md5}` | 查重（只读） |

AstrBot 插件（`main.py` + `imagelib.py`）—— 用了 5 个：

| 接口 | 用途 | 备注 |
|---|---|---|
| `POST /api/images/upload` | 上传 | 写 |
| `GET /api/images/check-md5/{md5}` | 查重 | 只读 |
| `POST /api/search` | 搜索 | 只读 |
| `GET /{kind}/{rel}` | 取图/缩略图 | 只读 |
| `POST /api/update_tags` | 改标签 | 写，但**有定义无调用**（死代码） |

**关键结论：两个 bot 都没有使用网页的 `/api/upload`。**

**本轮做法：不合并，两边各管各的。**

| 接口 | 本轮处理 |
|---|---|
| `POST /api/upload`（网页） | **加 `require_edit` 鉴权** |
| `POST /api/images/upload`（bot） | **保持开放**，本轮不动 |

**理由**

- 两个接口调用方零重叠，合并不是鉴权的前提；
- 合并要同步改 bot 插件（`main.py:704`、`__init__.py:127`），
  而 bot 代码改动本就有风险（日均上千张入库，改坏了会静默失败）；
- **先让网站有身份验证**是本轮目标，bot 暂不受影响。

**后续（下一轮再合并）**

合并为 `POST /api/images/upload` 一个接口，届时：

1. 改 bot 的 URL（AstrBot `main.py:704` / `imagelib.py:463`、nonebot2 `__init__.py:127`）；
2. 改前端 `Gallery.vue:549`；
3. 删除 `main.py:579` 的 `upload_file()`；
4. 给统一后的接口加"网页认 client_id、bot 认 token"的双凭据判断。

> 在此之前，`/api/images/upload` 是**未鉴权的写入口** —— 这是一个已知的
> 临时安全缺口，靠它只被 bot 调用、而 bot 不暴露给浏览器来缓解。
> 若本轮就想堵上，可给它加「只接受来自 127.0.0.1 的请求」作为过渡。

### 3.7 机器人身份：下一轮再处理

**本轮不改 bot 代码。** 机器人继续以未鉴权方式调用 `/api/images/upload`。

下一轮合并接口时，按此方案给机器人一个长期身份：

- 在 `auth_granted_clients` 中手工插入一条固定记录（`client_id = "bot"`）；
- 机器人在上传请求头带 `Authorization: Bearer <BOT_TOKEN>`；
- `require_edit` 同时接受两种凭据：请求体里的 `client_id`（网页）、
  请求头里的 token（bot）。

**配置方式**（下一轮实施时）

```ini
# backend/.env 或环境变量
BQBQ_BOT_TOKEN=<一段足够长的随机串，至少 32 字符>
```

机器人插件侧在同一份配置里读同一个值（`_conf_schema.json` 新增一项）。

**好处**

- 不需要为 bot 单独开鉴权豁免分支 —— 它和网页走**同一个** `require_edit`，
  只是凭据来源不同（网页用请求体里的 `client_id`，bot 用请求头里的 token）；
- 少一个"特殊放行"的安全口子；
- bot 侧改动极小：上传时多带一个请求头。

> **bot 调用的另一个接口** `GET /api/images/check-md5/{md5}` 是只读，
> 不需要鉴权，无需改动。

```html
  <!-- 登录态圆点：与 #hq-status-dot 完全同一套写法 -->
  <div
    id="login-status-dot"
    :class="['w-2 h-2 rounded-full mt-0.5',
             isLoggedIn ? 'bg-emerald-500' : 'bg-slate-300']"
  ></div>

  <!-- hover 提示：与 #fab-import / #fab-export 一致 -->
  <span class="absolute right-full mr-3 bg-slate-800 text-white text-xs px-2 py-1
               rounded opacity-0 group-hover:opacity-100 transition whitespace-nowrap
               pointer-events-none">
    {{ isLoggedIn ? '已登录' : 'QQ 登录' }}
  </span>
</button>
```

**为什么这样设计**

| 决策 | 理由 |
|---|---|
| **替换而非新增** `#fab-import` | 保持网格 10 个不变，布局不受影响 |
| `flex-col` + 图标 + 圆点 | 与 `#fab-hq` 的「HQ 文字 + 状态圆点」结构同构 |
| `w-14 h-14 rounded-2xl shadow-lg` | 与其它 9 个按钮完全一致 |
| `group-hover` 文字提示 | 与 `#fab-export` / `#fab-import` 一致 |
| 已登录绿、未登录灰 | 与 `#trash-active-dot` / `#hq-status-dot` 的色语义一致 |

> **导入功能去哪了？** 接口已随本次改动废弃（见 3.4.1），
> JSON 导入导出整体停用、改用直接备份 `meme.db`。
> 因此 `#fab-import` 让位给登录按钮**不会丢掉任何在用功能** ——
> 前端按钮暂时保留（点击时给出"已停用"提示），后续再清理。

#### 3.8.2 登录流程：toast 引导，不弹窗

```
点击「QQ 登录」按钮
   ↓
POST /auth/request { client_id }  ->  { code: "4821" }
   ↓
toast.info('验证码 4821，请私聊机器人发送「bqbq登录 4821」，5 分钟内有效', 10000)
   ↓  按钮进入「等待确认」状态（旋转图标）
轮询 GET /auth/me（每 2 秒）
   ↓
成功 -> toast.success('登录成功') + 按钮变绿 + 圆点变绿
超时 -> toast.warning('验证码已过期，请重新点击登录')
```

**关键点**

- **验证码放在 toast 里显示**，不占用额外 UI。toast 已有 3 秒自动消失机制，
  这里传 `duration = 10000`（10 秒）保证能看清。
- **不新增弹窗组件** —— 验证码直接通过 toast 展示，登录全程不使用模态框。
- toast 消失后若还没确认，用户忘了验证码怎么办？——**再次点击登录按钮
  会重新申请**，旧码作废，新码再 toast 一次。不需要提供"查看当前验证码"。

#### 3.8.3 未登录时的 401 引导

任何写操作返回 401：

```
toast.warning('请先登录 QQ 再操作（点击右侧盾牌按钮）')
+ 登录按钮加一个脉冲高亮动画（如 animate-pulse，3 秒后移除）
```

**不使用弹窗，不阻断操作**，用户自己决定何时点。

#### 3.8.4 收起态（FAB 迷你条）不设登录入口

**明确：迷你条不新增登录按钮。** 登录入口只放在展开后的 FAB 网格里。

理由：

- 迷你条（`#fab-mini-strip`）定位是"常用快捷操作"（清空/刷新/搜索），
  塞入低频的登录会破坏它的简洁性；
- 收起态下用户本来就不方便做管理类操作，需要的自然会展开。

**但有一个体验问题要处理**：如果用户在收起状态下触发写操作收到 401，
toast 里必须告诉用户"先展开 FAB"，否则会找不到按钮：

```
toast.warning('请先登录：展开右侧悬浮按钮组，点击「QQ 登录」')
```

**轮询代价**：仅登录过程中轮询 `/auth/me`（间隔 2 秒，最多 5 分钟）。
日常使用零轮询。这是唯一新增的轮询，且生命周期很短。

## 四、延迟影响汇总

| 场景 | 现在 | 加鉴权后 | 变化 |
|---|---|---|---|
| 浏览/搜索/翻页 | 860ms × N | 860ms × N | **无变化**（只读不校验） |
| 打标签 | 860ms | 860ms + 查表(~0.1ms) | **无感知** ✅ |
| 改规则 | 860ms | 860ms + 查表(~0.1ms) | **无感知** ✅ |
| 首次登录 | — | 一次 860ms（申请码） + QQ 消息 | 一次性 |
| 有效期 | — | **永不过期** | 验证一次长期有效 |

**结论：不会让延迟翻倍。** 写操作只多一次本机 SQLite 主键查询，
唯一新增的固定开销是首次登录那一次。

## 五、安全考虑

| 风险 | 对策 |
|---|---|
| 陌生人打开网站就想改数据 | 他的 client_id 不在 `auth_granted_clients` 表里 → 401 |
| 验证码被猜中 | 4 位 = 1 万种；有效期 5 分钟 + 每个 client_id 限次（如 5 次/小时）+ 用后即焚 |
| 验证码在 QQ 里被看到 | 私聊只有自己可见；且码只用于把**发起请求的那个 client_id** 写进授权表，别人拿到码也没用（除非同时控制了那个浏览器） |
| 知道他人 client_id 并拷到自己浏览器 | ⚠️ 理论上可冒用。但 client_id 只存在于本人 localStorage 与请求体中，不外露；真要注销，删授权表那一行即可 |
| **机器人长期 token 泄露** | 单独一条记录、可随时删表吊销；token 只存在 bot 配置里，不经浏览器 |
| 非管理员冒充 | bot 侧用现成的 `_is_admin()` 把关（读 AstrBot 的 `role`），非管理员直接拒绝 |

**注意**：官方机器人拿到的是 **openid 而非 QQ 号**，所以任何 openid
比较都必须用 openid 形式（可用现有 `bqbq绑定` 命令让用户自查）。

**两条凭据线并存**

| 主体 | 凭据 | 理由 |
|---|---|---|
| 网页浏览器 | `client_id`（服务端记授权） | 浏览器本来就有，无需额外下发 |
| 机器人 | 本轮无（接口暂不鉴权） | 下一轮合并接口时再配长期 token |

## 八、备选简化方案（如果连 bot 改造都想省）

**纯验证码 + 网页直接确认**（不经 QQ）：

- 验证码在网页生成并显示，用户手工输入确认。
